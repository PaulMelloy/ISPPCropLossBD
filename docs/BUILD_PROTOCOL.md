# Crop Loss Database: Build Protocol (Iteration 1)

**Purpose.** Step-by-step method for building a working prototype of the 
ISPP (ISPP) Crop Loss Subcommittee database: R Shiny front end, PostgreSQL 
back end, ORCID sign-in, and a full audit trail. 
The prototype is hosted on the ARDC Nectar Research Cloud and is meant to be 
shown to Dr Serge Savary and the subcommittee before approaching ARDC about 
interim hosting.

**What iteration 1 delivers.** 
Anyone can browse observations. 
Signed-in contributors can submit and edit their own observations. 
Curators can approve other people's submissions. 
Every insert and edit is logged with who, when, what changed and why, and that 
history is visible from each record.

**What it deliberately leaves out.** 
Data entry for the `crop_loss_meta` table and for studies, bulk upload, 
data export, map view, and fine-grained database row security. 
These are listed in Phase 6 as candidates for iteration 2, after committee 
feedback.

## 1. Decisions already made

| Decision | Choice | Reason |
|---|---|---|
| Database | PostgreSQL 16 | Relational data, strong constraints, JSON support for the audit trail, mature hosting options |
| Version control | Audit table populated by triggers, JSON diffs | One place to query history; app code cannot forget to log |
| Login | ORCID OAuth only (`/authenticate` scope) | Researcher identity, free, globally recognised |
| Prototype stack | R Shiny + `bslib` | Fastest path; familiar to the plant pathology community |
| Long-term stack | Python (Flask or FastAPI), rebuilt after committee feedback | Better suited to a maintained public service |
| Core table | `crop_loss` holds only the minimum required fields | Low barrier to contribution |
| Extra detail | Relational tables (`crop_loss_meta`, `study`) | Heterogeneous data without bloating the core table |
| Hosting path | Nectar (prototype) → ARDC (interim) → FAO (long term, aspirational) | |

**One architectural rule runs through everything:** business rules live in the database, not in R. Required fields, ranges, the yield loss calculation, the no-self-approval rule, permissions and the audit trail are all SQL. The Shiny app re-checks some of them only to give friendly error messages. This means the Python rewrite replaces the app layer only; the database and its history carry over untouched.

## 2. Changes from the Google Sheet draft

These are the deliberate differences between `inst/sql/001_schema.sql` and the committee sheet. Each is a proposal to confirm with the committee.

| Sheet | Prototype | Why |
|---|---|---|
| `group_id` (undefined) | Foreign key to a `study` table | Groups observations from one study, trial or meta-analysis |
| `pathogen` | `pathogen` (taxonomic, genus or species) plus `pathogen_common_name` and `agent_group` | Keeps taxonomy clean while allowing search by common name or broad class |
| `location` | `location` (text, required) plus optional `latitude` / `longitude` | Text always works; coordinates enable mapping later |
| `severity_units` under "Other variables?" | `severity_unit`, required whenever severity is given | Severity values are uninterpretable without units |
| (none) | `measurement_method`, required | Field survey, harvested plot, remote sensing and models are not directly comparable |
| `yield_loss` typed in | Calculated automatically as `yield_attainable - yield` | Cannot disagree with the two yields |
| `submitting_person` (ORCID / name / email) | ORCID from login, filled automatically | No typing, no impersonation |
| `approving_person` required at entry | Filled when a curator approves; `status` column added | Approval happens after submission |
| Rows deleted | Never deleted by the app; `status = 'withdrawn'` instead | Nothing disappears from the record |
| Meta-data tab, ids like `Meta-0001`, `cl-0001` | `crop_loss_meta` with integer ids, columns renamed to snake_case | Database-friendly names; ids generated by Postgres |
| `meta_data` free text | Kept as free text | Placeholder until patterns emerge from real submissions |

## 3. Open questions for Serge and the committee

These are the questions where the prototype had to guess. Raise them at the demo.

1. **Yield units.** Is t/ha the only unit, or should relative loss (%) be accepted for studies that report only percentage loss? If so, should `yield` and `yield_attainable` stay required?
2. **Controlled vocabularies.** Are the starting lists for measurement method, severity units and agent group (`inst/sql/004_seed.sql`) right?
3. **Standard identifiers.** Should crops and agents carry EPPO codes, or GBIF / NCBI taxonomy ids, alongside the names? This would make cross-study queries reliable.
4. **Multiple agents.** How should co-infections or pest complexes be recorded: one row per agent, or a link table?
5. **Curation.** Who are the curators, and can a curator approve their own submission? (The prototype says no.)
6. **Data licence.** CC BY 4.0, CC0, or another licence for contributed data? This must be settled before real data are collected.
7. **Privacy.** Contributors' names and ORCID iDs are stored and displayed. A short privacy statement is needed, particularly for contributors in the EU (GDPR).
8. **Variance definition.** Do the `*_var` fields hold standard deviation, standard error or variance? This needs a single definition, or a units field.

## 4. Phase 0: Local environment

**Goal:** develop and test on your own machine before touching Nectar.

1. Install R ≥ 4.3 and RStudio or Positron.
2. Install PostgreSQL 16 locally, **or** run it in Docker with `docker compose -f dev/docker-compose.yml up -d`.
3. Install the `psql` command-line client (comes with PostgreSQL).
4. Unzip `croplossdb` and open it as an RStudio project. Initialise git and push to a GitHub repository (the organisation or your own account). This repository becomes the shared codebase.
5. Install R dependencies:
   ```r
   install.packages(c("shiny", "bslib", "DT", "DBI", "RPostgres", "pool",
                      "httr2", "jsonlite", "openssl", "htmltools",
                      "pkgload", "testthat", "devtools"))
   ```
6. Run the unit tests (they don't need a database):
   ```r
   devtools::test()
   ```

**Checkpoint:** all tests pass.

## 5. Phase 1: Database

**Goal:** create the schema, audit trail, application role and seed data, and verify the audit trail works before any R is involved.

1. Run the setup script:
   ```bash
   OWNER_URL=postgres://croploss_owner:owner_dev_password@localhost:5432/croploss \
   APP_PASSWORD=app_dev_password ./dev/setup_db.sh
   ```
   This runs, in order:
   - `001_schema.sql`: tables, constraints, lookup tables, `updated_at` triggers
   - `002_audit.sql`: `crop_loss_audit` table and the `fn_audit()` trigger
   - `003_roles.sql`: the `croploss_app` login role with least privilege
   - `004_seed.sql`: vocabularies and the wheat / *Fusarium* example row from the sheet

2. Verify the audit trail by hand, connected as the app role:
   ```bash
   psql postgres://croploss_app:app_dev_password@localhost:5432/croploss
   ```
   ```sql
   -- Should FAIL: the app must say who is making the change
   UPDATE crop_loss SET yield = 2.6 WHERE id = 1;

   -- Should SUCCEED and be logged
   BEGIN;
   SELECT set_config('croploss.current_orcid', '0000-0002-1825-0097', true);
   SELECT set_config('croploss.change_comment', 'testing audit', true);
   UPDATE crop_loss SET yield = 2.7 WHERE id = 1;
   COMMIT;

   SELECT change_type, changed_by_orcid, old_values, new_values, change_comment
     FROM crop_loss_audit ORDER BY audit_id;

   -- Should FAIL: the app cannot delete, write the audit table, or change roles
   DELETE FROM crop_loss WHERE id = 1;
   INSERT INTO crop_loss_audit (table_name, record_id, change_type) VALUES ('x', 1, 'INSERT');
   UPDATE app_user SET role = 'admin';
   ```
   The update row should show `{"yield": 2.5, "yield_loss": 0.6}` → `{"yield": 2.7, "yield_loss": 0.4}`. Only changed fields are stored in `old_values` / `new_values`; the full prior row is in `row_snapshot`.

3. Promote yourself to curator or admin (as the owner, not the app role) after you first sign in:
   ```sql
   UPDATE croploss.app_user SET role = 'admin' WHERE orcid = '<your-orcid>';
   ```

**How "who made the change" works.** Each write from the app runs in a transaction that first calls `set_config('croploss.current_orcid', ..., true)`. The `true` makes the setting local to that transaction. The trigger reads it and refuses writes from `croploss_app` that don't set it. The R function `db_write()` in `R/db.R` does this for every write. The Python rewrite only needs to do the same two `set_config` calls.

**How to revert an edit (manual, for now).** Find the audit row, then copy the values from `old_values` back with an `UPDATE` in a transaction that sets `croploss.change_comment` to `'Reverted audit <id>'`. The revert is itself logged. A "revert" button is an iteration 2 candidate.

**Checkpoint:** the four "should fail" statements fail, and the update shows up in `crop_loss_audit` with your ORCID and comment.

## 6. Phase 2: Run the app locally

**Goal:** a working app on your machine, using the development login bypass.

1. Copy `dev/Renviron.example` to `.Renviron` in the project root.
2. Set the database variables to match Phase 1, and uncomment `CROPLOSS_DEV_AUTH` (this skips ORCID and signs you in as that iD). ORCID variables can stay as placeholders for now, but `CROPLOSS_STATE_SECRET` needs any value.
3. Run `source("dev/run_dev.R")`.
4. Walk through the full cycle:
   - Browse tab shows the seed row.
   - Add observation: submit a new entry. Try leaving out a required field to see validation messages.
   - Select your entry: summary shows "Submitted by Development User on ...".
   - Edit: change the yield, enter a reason, save. Summary now says "Edited 1 time by ...".
   - Full change history: one row per changed field, old and new value, ORCID link and comment.
5. Test approval: set your dev user to `curator` in SQL, set `CROPLOSS_DEV_AUTH` to a different iD, restart, and approve the seed row (you can't approve your own).

**How the app is organised** (see section 12): `R/app.R` assembles the UI and server; `R/mod_browse.R` is the table, record detail, history and edit; `R/mod_entry.R` is the new-entry form; `R/form.R` holds the form shared by both; `R/db.R` holds all SQL; `R/auth_orcid.R` handles sign-in.

**Checkpoint:** you can create, edit and approve, and the history view matches what you did.

## 7. Phase 3: ORCID sign-in

**Goal:** real ORCID login, tested against the ORCID sandbox before using production credentials.

1. **Create a sandbox account** at `https://sandbox.orcid.org`. Sandbox only sends email to Mailinator addresses, so register with one.
2. **Register a sandbox client** under *Developer tools* in the sandbox account. Add the redirect URI exactly as the app will use it, for example `https://croploss.example.org/`. Note the client id (`APP-...`) and secret.
3. Set `ORCID_ENV=sandbox`, `ORCID_CLIENT_ID`, `ORCID_CLIENT_SECRET`, `ORCID_REDIRECT_URI`, and a long random `CROPLOSS_STATE_SECRET`. Remove `CROPLOSS_DEV_AUTH`.
4. ORCID requires the redirect URI to match what is registered. In practice the cleanest way to test is on the Nectar instance with HTTPS (Phase 4), so steps 1–3 can be done now and tested after Phase 4.
5. **The flow** (implemented in `R/auth_orcid.R`):
   - The "Sign in with ORCID" button links to `/oauth/authorize` with `scope=/authenticate` and a signed, time-limited `state` value.
   - ORCID sends the user back to the redirect URI with `?code=...&state=...`.
   - The server checks the state signature and age, exchanges the code at `/oauth/token`, and reads `orcid` and `name` from the token response.
   - The user is upserted into `app_user` and the query string is cleared.
6. **Production credentials.** Once sandbox login works, register the public API client on your real ORCID record (*Developer tools*), switch `ORCID_ENV=production`, and swap the client id and secret. The public API is free and the `/authenticate` scope is all this app needs.

**Known limitation in iteration 1:** the login is held in the Shiny session, so reloading the page signs the user out. Two fixes for iteration 2: a signed session cookie, or putting `oauth2-proxy` in front of the app at the nginx level (ORCID supports OpenID Connect). The proxy option also carries over directly to the Python version.

**Checkpoint:** you can sign in with a sandbox ORCID account on the deployed app and your name appears in the navbar.

## 8. Phase 4: Deploy to Nectar

**Goal:** the app running at an HTTPS address you can send to Serge.

### 8.1 Instance

1. Sign in to the Nectar dashboard with your institutional login and pick the allocation to use.
2. Launch an instance: Ubuntu 24.04 LTS image, a small flavour (2 vCPU and 4–8 GB RAM is plenty for the prototype), your SSH key pair.
3. **Create a separate volume** (e.g. 20 GB), attach it, and put the PostgreSQL data directory on it. Instances can be rebuilt; volumes survive.
4. **Security groups:** SSH (22) from your institutional IP range only; HTTP (80) and HTTPS (443) from anywhere. Do not open 5432 or 3838.
5. Get a DNS name pointing at the instance's public IP, either through Nectar's DNS service for your project or a subdomain from your institution. Let's Encrypt needs a real hostname.

### 8.2 Software

```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y postgresql nginx certbot python3-certbot-nginx \
                    r-base r-base-dev libpq-dev libssl-dev libcurl4-openssl-dev gdebi-core
```

- **R packages:** install from binaries to save a lot of compile time, using either Posit Public Package Manager's Ubuntu binaries or r2u (CRAN as apt packages). Install them system-wide so the `shiny` user can see them.
- **Shiny Server (open source):** download the current `.deb` from Posit and install with `sudo gdebi shiny-server-*.deb`.
- **The app package:** `sudo R -e 'remotes::install_github("<you>/croplossdb")'` (or install from the local source).

### 8.3 Database

1. Move the PostgreSQL data directory to the attached volume (or initialise the cluster there).
2. Create the database and an owner role, then run `dev/setup_db.sh` with a strong `APP_PASSWORD`.
3. Confirm `listen_addresses = 'localhost'` in `postgresql.conf`.

### 8.4 App and web server

1. `sudo mkdir -p /srv/shiny-server/croploss` and copy `deploy/app.R` into it.
2. Create `/srv/shiny-server/croploss/.Renviron` from `dev/Renviron.example` with production values. Then `sudo chown shiny:shiny .Renviron && sudo chmod 600 .Renviron`. **Do not** set `CROPLOSS_DEV_AUTH`.
3. Copy `deploy/shiny-server.conf` to `/etc/shiny-server/shiny-server.conf` and `sudo systemctl restart shiny-server`.
4. Copy `deploy/nginx-croploss.conf` to `/etc/nginx/sites-available/croploss`, replace the hostname, symlink into `sites-enabled`, `sudo nginx -t && sudo systemctl reload nginx`.
5. `sudo certbot --nginx -d <your-hostname>` for HTTPS.
6. Set `ORCID_REDIRECT_URI` to `https://<your-hostname>/` and make sure it matches the ORCID client registration exactly.

### 8.5 Backups

1. Install `deploy/backup.sh` in the `postgres` user's crontab (nightly `pg_dump`, 14 days kept).
2. Copy dumps **off the instance**, for example to Nectar object storage with `rclone`.
3. Do one test restore into a scratch database. A backup that has never been restored is not a backup.

**Checkpoint:** `https://<your-hostname>/` loads over HTTPS, ORCID sign-in works, and a nightly dump appears in object storage.

## 9. Phase 5: Hardening before the demo

Work through this list before sending the link to anyone.

- [ ] `CROPLOSS_DEV_AUTH` is not set on the server.
- [ ] Strong, unique passwords for the database owner and `croploss_app`; `.Renviron` is `chmod 600`.
- [ ] Unattended security upgrades enabled (`sudo apt install unattended-upgrades`).
- [ ] Server firewall (`ufw`) allows only 22, 80, 443.
- [ ] You and at least one other person have `admin` / `curator` roles.
- [ ] A test restore from backup has been done.
- [ ] 10–20 real observations from published studies entered (ideally from the committee's own meta-analyses) so the demo isn't empty. Real data will also stress-test the schema faster than any discussion.
- [ ] A banner or About-page note that this is a prototype and data may be reset.
- [ ] A draft data licence and privacy statement on the About page (see open questions 6 and 7).
- [ ] Tried on a phone and in a second browser.
- [ ] Shiny Server logs (`/var/log/shiny-server`) show no errors after a full walkthrough.

## 10. Phase 6: Demo, feedback, iteration 2

1. **Serge first.** Send the link with a short note: what it does, the open questions from section 3, and a request to try adding one observation from a paper he knows well.
2. **Then the subcommittee.** A 15-minute walkthrough: browse, sign in, add, edit, show the history. Then the open questions.
3. **Capture feedback as GitHub issues**, one per point, labelled `schema`, `ui`, `workflow` or `question`. This creates a public record of how the design was decided.
4. **Schema changes go in new numbered migration files** (`005_....sql`, `006_....sql`), never by editing `001_schema.sql` once real data exist. A tool like `sqitch` or `dbmate` can be adopted when changes become frequent.

**Iteration 2 candidates** (prioritise from feedback):
- Entry forms for `crop_loss_meta` and `study`
- Bulk upload from CSV/Excel matching the committee template, with validation preview
- Data export (CSV) of approved records, with a citation and licence
- Map view using the coordinates
- Persistent login (signed cookie or `oauth2-proxy`)
- Revert button in the history view
- Row-level security in Postgres so edit/approve permissions are enforced by the database, not only by the UI
- Search by EPPO code or taxonomy id, if the committee adopts identifiers

## 11. Phase 7: Preparing for the Python rewrite and handover

Because the rules live in SQL, the rewrite is mostly a port of the presentation layer.

**What carries over unchanged:** all of `inst/sql/`, the data, the audit history, the role model, the `set_config` convention for recording the ORCID on each write.

**What gets rewritten:**

| R prototype | Python equivalent |
|---|---|
| `R/db.R` (DBI + pool) | SQLAlchemy Core or `psycopg` with a connection pool |
| `R/auth_orcid.R` | Authlib (OAuth/OIDC client), or keep `oauth2-proxy` at nginx |
| `R/validate.R` | Pydantic models |
| Shiny modules | FastAPI endpoints + a front end (HTMX/Jinja templates is the lightest; React if needed) |
| `tests/testthat` | `pytest` |

**For ARDC and eventual FAO handover, have ready:** the GitHub repository, this protocol, a data dictionary generated from the database (column comments), the licence, the privacy statement, backup and restore instructions, and expected data volume. A useful rough estimate for the conversation: even 100,000 observations with history is well under 1 GB, so storage is not the constraint. Maintenance and governance are.

```
│   ├── app.R           UI layout and top-level server

│   ├── mod_entry.R     New observation form
│   ├── run_app.R       run_app() entry point
│   ├── utils.R         Config, helpers, ORCID links
│   └── validate.R      Friendly validation messages
├── inst/sql/
│   ├── 001_schema.sql  Tables, constraints, vocabularies
│   ├── 002_audit.sql   Audit table and trigger

```
